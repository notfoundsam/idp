# ADR-009: AWS infrastructure

## Status

Accepted

## Decision

- **Accounts and state:** staging and production live in AWS accounts of their own. `infra/terraform/bootstrap` gives each a state bucket encrypted by its own KMS key with S3 lock files, and roles for GitHub Actions through OIDC: `terraform` for the GitHub environment `<env>-infra`, `deploy` for `<env>`.
- **Network:** the private subnets have no route to the internet. Tasks reach AWS through VPC endpoints, and each workload has a security group to which the module that connects two workloads adds the rules of both sides.
- **Credentials:** Terraform generates every credential of the services into Secrets Manager: passwords, the Valkey token and the HMAC key of Throttle as write-only values, the SMTP credentials of SES from the access key of an IAM user, which lives in the encrypted state. RDS manages its master password itself. ECS hands secrets to the containers as variables, and the images of `infra/` turn them into the files their programs read.
- **TLS:** every connection is TLS, and every client of an internal service verifies the certificate and its name, and trusts the roots of one issuer alone. Internal hosts get certificates from the CA of `modules/pki`, whose key lives only in the encrypted state: PgBouncer, the collector, and `app` and `ops` behind their ALBs, which verify no target. RDS is trusted through its roots for the region, ElastiCache through the roots of Amazon Trust Services. The JDBC URLs use `SingleCertValidatingFactory`, `app` its own trust manager for Valkey and the exporters an SSL bundle, each with the certificates in a variable, so the images carry no trust store.
- **Telemetry:** an OpenTelemetry Collector of its own writes the OTLP lines to CloudWatch Logs, the metrics to CloudWatch through EMF and the spans to X-Ray with Transaction Search, all through interface endpoints. The services only write: their roles reach none of these stores, and every log group has deletion protection.
- **Edge:** the public ALB takes requests only from CloudFront: through the managed prefix list of its origin-facing servers and a generated header that the listener requires. A WAF on the distribution limits each viewer address, and `app` reads that address only from `CloudFront-Viewer-Address`.
- **Services:** `app`, `worker` and `ops` are ECS services, `migrator` and the operator CLI one-off tasks, all with a read-only root. `ops` answers only on an internal ALB that the VPN reaches, while its service tenant `ops-sso` stays behind CloudFront. Staging runs the Spring profile `staging`, which is `prod` except that a load test may switch the limits of `app` off.
- **Rights:** each task has a task role of its own in `modules/iam`. IAM grants the rights on keys and buckets that exist before the services, and the key policy that `worker` attaches to every tenant KEK at `CreateKey` grants the rights on it. Key policies deny by `aws:PrincipalArn`: `ops` and the CLI only encrypt with the platform KEK and reach no tenant KEK, only `app`, `worker` and the recovery run decrypt a tenant KEK, and only `worker` and the recovery run delete one. The recovery run is a task definition of its own for `migrator` after a restore, so a release holds no right in AWS.
- **Database bootstrap:** RDS has no superuser, so a one-off task creates `idp_owner` and `provisioner` as the master user, and another sets the passwords of the runtime roles as `idp_owner` after `migrator` created them.

## Rationale

Without a route out, a compromised task can reach only the AWS services and the hosts its security group names. Write-only secrets keep passwords out of the plan, the state and CI logs, which a generated value in a regular attribute would not. SES offers SMTP only with credentials derived from an IAM access key, so that key is the one generated credential in the state. One issuer per connection means a certificate from any other CA cannot impersonate the database, Valkey or the collector. CloudWatch and X-Ray need no servers of ours, take their periods per log group and answer inside the VPC, and a collector between them and the services keeps AWS credentials and the routing of `idp.security` out of the services, which then cannot touch what they logged. Behind CloudFront the ALB sees only edge servers, so only the edge can count by viewer, and only a header that CloudFront overwrites carries the viewer to `app`. The prefix list admits the distributions of every account, so the header proves that a request passed this one and its WAF. The API of the operator reaches every tenant record of `platform`, so nothing on the internet may reach it. A load test measures the capacity behind the limits, and a profile of its own keeps that switch out of production. A tenant KEK has no ARN until `worker` creates it, so only a policy that comes with the key can scope rights to tenant KEKs alone, and a deny in the key policy outlasts any IAM policy granted later, even an administrator's. A role created again keeps its ARN but not its principal ID, so conditions on the ARN keep holding where a principal would lock the services out of every tenant KEK. KEKs are destroyed again only after a restore, and permanent rights would let every release of `migrator` erase tenants. A private CA in the state needs no protection beyond what the state already has, where AWS Private CA would add a monthly fee per environment for a few certificates. The same images and scripts run against plain Postgres, so an on-premises installation keeps them.
